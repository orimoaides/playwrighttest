02 — Roadmap

3フェーズ構成

実装済 フェーズ①

Gemini Canvas 版（単一HTML）。ブラウザ内で完結する動く骨格。スクショはダミー。

役割: データ契約の確定とデモ。

実装済 フェーズ②

ブラウザアプリ版（フロント＋Nodeサーバー）。実 Playwright で巡回・実スクショ・ログ取得。

役割: 本番品質のエンジン。

設計中 フェーズ③

CLI + MCP 版。②のエンジンを core 化し、AIエージェントやCIから自律的に呼べる部品に。

役割: 自動化・組み込み。

①②は実装・検証済み（PRオープン）。③に進むか、②を磨くかが目下の分岐。

03 — Core Constraint

なぜ Canvas は外部サイトを
直接取得できないのか

ブラウザの同一オリジンポリシー（CORS）。 ページのJSは原則自分のサイトからしかデータを取れない。Canvas はブラウザ内で動くため、この制約をそのまま受ける。

あなたのコード
Canvas内のJS
→
警備員 = CORS
他サイトは遮断
✕ blocked
外部サイト
members.co.jp

なぜ存在する? 悪意あるページが、裏であなたのログイン中のGmailや銀行を読むのを防ぐため。あなたを守るルールであり、無効化はできない。

→ サーバー（Node）には警備員がいない。だから「自前サーバーが取りに行く」フェーズ②は URL だけで巡回できる。

06 — Decisions (1/2)

決めなきゃいけないこと

A. 主軸の配信形態は？
Canvas単体 / ローカル実行アプリ / 常駐サーバー / CLI・MCP　— 誰がどう使う？
B. APIキーの置き場所
フロント（手軽・露出リスク） vs サーバーenv（安全）　— ②は後者で実装済み
C. 外部サイトの取得手段
CORSプロキシ（第三者経由・静的のみ） vs 自前サーバーPlaywright（全部○）
D. SPA（JS描画サイト）対応は必要？
必要ならサーバー/ローカルでの実ブラウザ実行が必須（ファイル読みでは不可）

※ 太字＝現状の推奨／実装済みの選択。

06 — Decisions (2/2)

決めること（つづき）

E. 認証付きサイトに対応する？
対応するならローカル/サーバー実行＋認証情報の受け渡し設計が必要
F. スクショの品質ライン
ダミー（①） vs 実Playwright・操作前後ペア＋赤枠ハイライト（②）　— 撮影安定化の作り込み量
G. 配布する成果物の形式
html（単一） / zip（画像分離） / site（複数ページ静的）　— どれを出す？
H. 安全装置のデフォルト強度
robots.txt尊重 / 破壊的操作の抑止 / 許可ドメインallowlist / 巡回上限　— どこまで堅く
I. 運用形態
ローカル実行（npm start） vs Playwright公式Dockerで常駐
07 — Recommendation

推奨ルートと次の一手

本命は「サーバー実行」

  • URLだけで巡回・SPA・認証すべてに強い
  • APIキーをサーバーに隔離でき安全
  • ＝ フェーズ② が既にこの形

Canvasは「軽いデモ/手元」用

  • サーバー不要で配りやすい
  • ローカルファイル / HTML貼付で十分
  • 外部URLはプロキシ頼みで限界あり

次の一手の候補

  • フェーズ③へ：core を切り出して CLI＋MCP化（CIや Claude から呼べる部品に）
  • ②を磨く：実キーで一気通貫テスト・撮影品質・大規模サイトのレート制御
  • 配布形態の決定：社内ツールとして npm 起動 or Docker 常駐
08 — Summary

まとめ

  • 処理は routes→scenario→steps→manual の4段。データ契約は不変。
  • Canvas が外部URLを直接取れないのは CORS（安全のための仕様）。回避はプロキシ/ローカル/サーバー。
  • Canvas以外を含め取得は5方式。全部○なのはサーバー側 Playwrightだけ。
  • 主要な意思決定は 配信形態・APIキー・外部取得・SPA/認証・スクショ・DL形式・安全装置・運用。
  • ①②は実装/検証済み。分岐は「③に進む」か「②を磨く」か。
